# SPEC: Fraud Detection ML Pipeline

## 1. Problem Statement

This project demonstrates a realistic, if intentionally small, fraud-detection
ML pipeline: synthetic transaction data generation, feature engineering,
model training with class-imbalance handling, and fraud-appropriate
evaluation, all runnable locally as a batch CLI. The audience is engineers
and fintech practitioners evaluating engineering and ML judgment — the goal
is to demonstrate correct practice (leakage-free splits, imbalance-aware
metrics, model documentation), not to ship a production fraud system.

## 2. Scope

In scope:
- A synthetic transaction generator with non-trivial (not linearly
  separable) fraud patterns.
- Feature engineering including a leakage-safe velocity feature.
- A single sklearn `Pipeline` abstraction supporting two model types
  (logistic regression, random forest) selected by config, not code changes.
- Time-ordered (non-random) train/test split.
- Fraud-appropriate evaluation: PR-AUC as primary metric, a business-framed
  recall-at-fixed-precision number, and a confusion matrix at that
  operating threshold.
- A model card artifact documenting data provenance, limitations, and
  metrics.
- A CLI with `generate-data`, `train`, and `evaluate` subcommands.
- CI running lint, type-check, and test/coverage gates.

## 3. Non-Goals / Limitations

**No real transaction data exists or will be sourced in this project.** All
data is generated by a synthetic generator (Section 4) designed to have
realistic *structure* (mixed fraud signatures, class overlap, imbalance),
but it is not fit to, sampled from, or validated against any real payments
dataset. **Metrics produced by this pipeline are not a claim of real-world
fraud-detection performance** and must not be presented as such anywhere
(code comments, model card, README).

Explicitly out of scope:
- Real or third-party transaction datasets, PII, or regulated data of any
  kind.
- A `predict`/scoring CLI command for new unlabeled transactions. `evaluate`
  (which requires labels) is the only scoring-related command in this
  iteration.
- Any deployed service, API layer (FastAPI etc.), streaming/online
  inference, or cloud infra. This is a local batch CLI only.
- Resampling techniques (SMOTE, undersampling) — imbalance is handled via
  `class_weight` only (Section 6).
- Hyperparameter tuning/search infrastructure. Fixed, documented
  hyperparameters only.
- Model monitoring, drift detection, retraining automation.
- New runtime dependencies beyond pandas, numpy, scikit-learn, joblib
  (already in `pyproject.toml`), and stdlib `argparse` for the CLI. Dev-only
  additions of `ruff`, `mypy`, `pytest-cov` are in scope (Section 12).

## 4. Data: Synthetic Transaction Generator (`data.py`)

`generate_transactions(config: Config) -> pd.DataFrame` produces a raw,
timestamp-sorted DataFrame with one row per transaction. All randomness
uses `numpy.random.default_rng(config.random_seed)` so output is fully
reproducible for a fixed seed.

Raw schema (columns produced directly by `data.py`):

| column | type | notes |
|---|---|---|
| `transaction_id` | int | sequential |
| `customer_id` | int | drawn from a pool of `max(200, n_samples // 20)` customers, so customers repeat and a velocity feature is meaningful |
| `timestamp` | datetime | spread uniformly over the last `config.n_days` days, sorted ascending in the final output |
| `amount` | float | transaction amount |
| `account_age_days` | int | age of the account at transaction time |
| `distance_from_home_km` | float | distance between transaction location and customer's home |
| `merchant_category` | category | one of a fixed list, e.g. grocery, electronics, travel, restaurant, online, gas_station, entertainment, other |
| `is_foreign` | bool | transaction is in a foreign country |
| `is_fraud` | bool | target label |

Row count is `config.n_samples`; fraud rows are `round(n_samples *
config.fraud_rate)` of the total (base rate ~1-2%, configurable).

**Fraud must not be trivially separable.** Generate fraud rows as a mix of
three sub-populations (fixed internal proportions, not exposed via config):

1. **~40% "foreign + high-value + new-account"**: `is_foreign=True`,
   `amount` drawn from a higher-mean lognormal than legitimate transactions,
   `account_age_days` uniform in `[0, 30]`, `merchant_category` weighted
   toward electronics/travel/online.
2. **~40% "card-testing / velocity burst"**: generated as bursts of several
   transactions for the same `customer_id` within a short window (minutes),
   at unusual hours (forces `hour_of_day` into 0–5 at the raw-timestamp
   level), moderate amounts, and `distance_from_home_km` well above the
   legitimate distribution — this is what makes `transactions_last_24h`
   (Section 5) a genuinely predictive engineered feature.
3. **~20% "noise"**: sampled from the *same* distributions as legitimate
   transactions, just labeled fraud. This creates an irreducible error
   floor and prevents PR-AUC from trivially reaching 1.0.

Additionally, a small fraction (~2%) of *legitimate* transactions should be
generated with foreign+high-value characteristics (e.g. real business
travel), overlapping with pattern 1's feature distribution, so the fraud
signatures are not "any foreign+high-value transaction is fraud."

After generating legitimate and fraud rows, concatenate and sort the full
DataFrame by `timestamp` ascending before returning it (transactions
interleave in real chronological order, as they would in production).

## 5. Feature Engineering (`features.py`)

`add_features(df: pd.DataFrame) -> pd.DataFrame` takes the raw,
timestamp-sorted schema and returns a new DataFrame (does not mutate the
input) with derived columns:

- `amount_log = log1p(amount)` — reduces the influence of the heavy right
  tail of transaction amounts on linear models.
- `hour_of_day = timestamp.dt.hour`
- `is_weekend = timestamp.dt.dayofweek >= 5`
- `is_night = hour_of_day` in `[0, 5]` inclusive
- `transactions_last_24h`: for each row, the count of **other**
  transactions by the same `customer_id` with `timestamp` strictly in
  `(row.timestamp - 24h, row.timestamp)` — i.e. strictly in the past
  relative to that row, excluding the row itself and excluding anything at
  or after its own timestamp. This is a velocity/card-testing signal.

**Leakage rule**: `transactions_last_24h` must only ever count transactions
strictly earlier than the row being scored. It is computed once over the
full chronologically-sorted dataset (spanning both the eventual train and
test partitions) before the time split — this mirrors production, where a
customer's transaction history naturally spans the train/serve boundary,
and does not leak any *label* information, only prior *event* counts.

The resulting columns must satisfy exactly the field names already declared
in `Config.numeric_features` and `Config.categorical_features` (Section 8) —
`add_features` plus the raw schema's `merchant_category`/`is_foreign`
together produce every feature the model consumes.

## 6. Train/Test Split (`pipeline.py`)

Split is **time-ordered, not randomly shuffled**: sort by `timestamp`
ascending, take the first `1 - config.test_size` fraction as train and the
remaining, chronologically later, fraction as test.

*Why*: a random shuffle would let the model train on transactions that
occur after some of its test transactions, leaking future fraud-pattern
information (e.g. a fraud campaign's signature) into training in a way that
would never be available at real prediction time.

## 7. Class Imbalance Handling

Use `class_weight="balanced"` on the classifier (both logistic regression
and random forest support it natively in scikit-learn). Do **not** use
resampling (SMOTE, random oversampling/undersampling).

*Why*: `class_weight` requires no extra dependency, no synthetic
duplication of already-synthetic minority-class rows (which would risk
compounding unrealism), and keeps the pipeline a single deterministic
`fit()` call.

## 8. Model (`model.py`)

`build_pipeline(config: Config) -> sklearn.pipeline.Pipeline` returns an
**untrained** sklearn `Pipeline`:

1. A `ColumnTransformer`:
   - `config.numeric_features` → `StandardScaler()`
   - `config.categorical_features` → `OneHotEncoder(handle_unknown="ignore")`
2. A final estimator chosen by `config.model_type`:
   - `"logistic_regression"` → `LogisticRegression(class_weight="balanced", max_iter=1000, random_state=config.random_seed)`
   - `"random_forest"` → `RandomForestClassifier(class_weight="balanced", n_estimators=200, random_state=config.random_seed)`
   - any other value → raise `ValueError` with a clear message naming the
     two valid options.

Swapping models must be a **config change only** — no branching in
`pipeline.py` or `cli.py` beyond passing `config.model_type` through.

## 9. Evaluation (`evaluate.py`)

`compute_metrics(y_true, y_prob, target_precision: float) -> dict` returns:

- `pr_auc`: `sklearn.metrics.average_precision_score(y_true, y_prob)` —
  **primary metric**.
- `roc_auc`: `sklearn.metrics.roc_auc_score(y_true, y_prob)` — reported for
  reference only, explicitly labeled secondary.
- `threshold`, `recall_at_precision`: using
  `sklearn.metrics.precision_recall_curve`, find the threshold achieving
  the **highest recall among thresholds whose precision is >=
  `target_precision`**. If no threshold reaches `target_precision`, set
  `threshold=None` and `recall_at_precision=None` rather than raising — this
  is a valid outcome to surface, not an error.
- `confusion_matrix`: `{tn, fp, fn, tp}` computed at `threshold` (using 1.0
  — i.e. always-negative — if `threshold` is `None`, so the shape of the
  return value is stable).

*Why PR-AUC and recall-at-precision, not accuracy/ROC-AUC alone*: at a ~1-2%
fraud rate, a classifier that predicts "never fraud" scores ~98-99%
accuracy and can still show a deceptively strong ROC-AUC (the metric is
dominated by the huge true-negative population), while catching zero fraud.
PR-AUC and a precision-fixed recall number directly reflect the tradeoff a
fraud-ops team actually faces: for a fixed analyst review capacity
(precision), how much fraud do we catch (recall)?

`target_precision` comes from `config.target_precision` (Section 12,
default `0.90`) — the business framing is "flag transactions such that 90%
of flags are genuinely fraud; report what fraction of all fraud that
catches."

## 10. Model Card (`write_model_card`, in `evaluate.py`)

`write_model_card(config: Config, metrics: dict, path: str) -> None` writes
a markdown file to `config.model_card_path` containing, at minimum:

- A prominent statement that training/evaluation data is synthetic, and
  that results are not a claim of real-world fraud-detection performance.
- Config snapshot: `random_seed`, `n_samples`, `fraud_rate`, `test_size`,
  `model_type`.
- Metrics: `pr_auc`, `roc_auc`, `target_precision`, `recall_at_precision`,
  `confusion_matrix`.
- An "Intended Use" section stating this is for educational/portfolio
  demonstration of fraud-detection ML pipeline practices, and explicitly
  **not** for production fraud decisioning, credit decisioning, or any use
  affecting real customers.

## 11. CLI (`cli.py`)

Use stdlib `argparse` only. `main(argv: list[str] | None = None) -> int`,
runnable via `python -m fraud_detection.cli`. Subcommands:

- `generate-data [--output PATH] [--n-samples INT] [--fraud-rate FLOAT] [--seed INT]`
  — calls `data.generate_transactions`, writes CSV to `--output` or
  `config.data_path`, creating parent directories if needed.
- `train [--data-path PATH] [--model-type {logistic_regression,random_forest}] [--model-path PATH] [--test-size FLOAT] [--seed INT]`
  — reads the CSV, applies `add_features`, time-splits, builds and fits the
  pipeline, saves it via `joblib.dump` to `--model-path`/`config.model_path`,
  evaluates on the held-out test partition, and writes the model card.
  Prints a summary of the metrics to stdout.
- `evaluate [--data-path PATH] [--model-path PATH] [--target-precision FLOAT]`
  — loads a saved model and a CSV, applies `add_features`, time-splits
  using the same `test_size` logic, evaluates the model on the test
  partition only (never re-trains), and prints/writes metrics.

Invalid `--model-type` or a missing model/data file must exit non-zero with
a clear error message, not a stack trace or silent no-op.

## 12. Module Boundaries

- `data.py`: `generate_transactions(config) -> pd.DataFrame`. Pure, no I/O.
- `features.py`: `add_features(df) -> pd.DataFrame`. Pure, no I/O.
- `model.py`: `build_pipeline(config) -> Pipeline`. No training logic beyond
  construction; fitting happens by calling `.fit()` on the returned object.
- `evaluate.py`: `compute_metrics(...)`, `write_model_card(...)`. No I/O
  except the model card write.
- `pipeline.py`: orchestration only — `time_split(df, test_size)`,
  `run_generate_data(config)`, `run_train(config)`, `run_evaluate(config)`.
  All file I/O (reading/writing CSVs, `joblib.dump`/`load`, creating
  `data/`/`models/` directories) lives here, not in `data.py`/`model.py`.
- `cli.py`: argparse wiring only, calling into `pipeline.py`. No business
  logic.

## 14. Key Design Decisions

| Decision | Reason |
|---|---|
| Time-ordered split, not random | Random splits leak future transaction/fraud patterns into training. |
| `class_weight="balanced"`, not resampling | Simplest correct approach; avoids duplicating already-synthetic minority rows. |
| One sklearn `Pipeline`, model chosen by config | Swapping models is a config change, not a code change (implementor.md's dependency-direction guidance). |
| PR-AUC + recall-at-precision as primary metrics | Accuracy/ROC-AUC are misleading under ~1-2% class imbalance. |
| Fraud generated as 3 mixed sub-patterns + noise | Avoids trivial separability; gives a believable, sub-1.0 PR-AUC. |
| `transactions_last_24h` computed backward-only, pre-split | Realistic velocity signal without leaking future events into a row's features. |
| No `predict` command this iteration | Keeps scope to what's specified; unlabeled-scoring threshold persistence is a separate design question. |
